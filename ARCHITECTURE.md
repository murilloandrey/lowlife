# Lowlife Est. 15 Architecture

## What this project is

Lowlife Est. 15 is a custom storefront for a Houston car-show-culture and
streetwear brand. The customer-facing site is a purpose-built React application,
while Shopify is intended to provide the commerce and content backend. It is not
a Shopify theme and does not use Liquid: the frontend reads Shopify data through
GraphQL APIs and sends shoppers to Shopify's hosted checkout.

## Technology and operating model

- **TanStack Start, Vite, React 19, and SSR:** TanStack Start supplies file-based
  routing and server rendering, with Vite handling development and builds. The
  project was originally generated by Lovable, so several conventions and build
  plugins are inherited scaffold choices rather than hand-selected architecture.
  Read `Lowlife Ignition/AGENTS.md` before changing Git history or build setup;
  pushed commits sync back to Lovable.
- **Tailwind CSS v4 and shadcn/ui:** Tailwind provides the design tokens and
  utility styling in `src/styles.css`. The reusable primitives under
  `src/components/ui/` are shadcn-generated components. Prefer composing those
  primitives in section components; do not casually customize every generated
  primitive.
- **Shopify Storefront API:** Products, product variants, articles, images,
  carts, and checkout URLs are read or mutated through Shopify's versioned
  Storefront GraphQL API. This replaces Shopify's theme/Liquid rendering layer.
- **Shopify Admin API:** Newsletter signup is handled server-side through the
  Admin GraphQL API because creating/updating customers and marketing consent
  requires privileged credentials that must never reach the browser.
- **Shopify-managed content:** "Monthly Mag" is designed to use Shopify's native
  blog/articles. Gallery items and Owner Spotlight builds are modeled as Shopify
  metaobjects. This lets non-technical staff update editorial and community
  content in Shopify without a frontend code deployment.
- **Deployment:** The site is currently deployed through Vercel under the
  development agency's account, not the client's account. Deployment settings
  and environment variables therefore live in that Vercel project rather than
  in this repository. Coordinate ownership/access changes with the agency.

### Nitro and the Cloudflare-looking build output

The Lovable Vite preset configures Nitro with Cloudflare as its default build
target unless another target is configured. As a result, local and CI builds can
generate `.output/server/wrangler.json`, `.wrangler/`, and other
Cloudflare-shaped artifacts. They are build byproducts and **do not mean this
site is hosted on Cloudflare**; the current deployment platform is Vercel.
`vite.config.ts` intentionally delegates this setup to
`@lovable.dev/vite-tanstack-config`, and duplicating its plugins can break the
app.

## Repository structure

The Git repository root contains project-wide documentation and automation. The
actual application is nested one level down:

```text
.
├── .github/workflows/ci.yml
├── ARCHITECTURE.md
├── README.md
└── Lowlife Ignition/
    ├── AGENTS.md
    ├── .env.example
    ├── package.json
    ├── vite.config.ts
    └── src/
        ├── assets/
        ├── components/
        │   ├── sections/
        │   └── ui/
        ├── lib/
        │   ├── shopify/
        │   ├── mock-storefront-data.ts
        │   └── shopify-types.ts
        ├── routes/
        ├── router.tsx
        ├── server.ts
        └── styles.css
```

- `Lowlife Ignition/` is the application root. The nested folder and its
  space-containing name are Lovable artifacts, not deliberate conventions.
  Flattening/renaming it may be worthwhile later, but would require updating CI,
  deployment, aliases, and Lovable assumptions together.
- `src/routes/` contains TanStack Start's file-based routes. `__root.tsx` owns
  document metadata, error/not-found handling, and the React Query provider;
  `index.tsx` composes the homepage sections.
- `src/components/sections/` contains the homepage's domain-level components,
  including Shop, Events, Monthly Mag, Video Carousel, Gallery, Owner Spotlight,
  and Newsletter Popup.
- `src/components/ui/` contains mostly generated shadcn primitives. Treat it as
  low-level shared infrastructure and avoid broad hand edits.
- `src/assets/` contains the current local product and community photography
  used by fallback data.
- `src/lib/shopify-types.ts` defines the shared Shopify-shaped product, article,
  metaobject, event, video, and ticket types.
- `src/lib/mock-storefront-data.ts` holds typed local products, articles, events,
  gallery items, spotlight builds, and video cards.
- `src/lib/shopify/` is the integration layer:
  - `client.ts` reads public Storefront configuration and provides the GraphQL
    fetch wrapper and `isShopifyConfigured()`.
  - `operations.ts` contains product, article, gallery/metaobject, and cart
    GraphQL operations.
  - `hooks.ts` maps Shopify responses to shared types and provides React Query
    hooks with local fallbacks.
  - `cart.ts` creates/restores carts, adds variant lines, persists the cart ID in
    `localStorage`, and redirects to Shopify's `checkoutUrl`.
  - `newsletter.ts` is the browser client for the same-origin newsletter
    endpoint.
  - `newsletter.server.ts` performs privileged customer and marketing-consent
    writes through the Admin API.
- `src/server.ts` wraps the TanStack server entry, routes newsletter requests,
  and normalizes catastrophic SSR errors.
- `.github/workflows/ci.yml` is rooted at the repository level but runs commands
  from `Lowlife Ignition/`.

## Mock data and live Shopify

The central architectural rule is that UI components do not care whether their
data came from local files or Shopify.

`shopify-types.ts` defines component-facing types that mirror the fields selected
by the Storefront API queries. The mock arrays in `mock-storefront-data.ts`
satisfy those same types. Hooks such as `useShopifyProducts()`,
`useShopifyArticles()`, and `useShopifyGallery()` call
`isShopifyConfigured()` before making a network request:

1. With both public Storefront variables present, the hook requests Shopify,
   maps the GraphQL response to the shared type, and returns it through React
   Query.
2. Without credentials, the hook returns the corresponding local mock array
   without attempting a request.
3. If a configured request fails or returns no usable records, the current
   implementation logs a warning and falls back to local data so the storefront
   remains usable.

This is why mock data must not be deleted merely because Shopify is connected.
It keeps local development, previews, and outage behavior functional. Once a
store is provisioned, setting environment variables activates the existing live
path; Shop, Monthly Mag, Gallery, and Owner Spotlight should not need component
rewrites.

Cart behavior follows the same gate. With Shopify configured,
`useStorefrontCart()` uses `cartCreate`/`cartLinesAdd`, stores the cart ID under
`lowlife-shopify-cart-id`, and redirects to Shopify checkout. Without
configuration it maintains the current in-memory cart count and performs no
Shopify calls.

Events and the video carousel are currently exceptions: both read local arrays
directly. Events have only a demo QR flow, and video posts have placeholder
thumbnails with null embed URLs. They need dedicated data/integration work
before they are remotely managed.

Comments beginning with `TODO(shopify)`, `TODO(owner-data)`, or
`TODO(client-content)` mark known handoff points, not abandoned code. Search
them before integration work:

```sh
grep -RInE 'TODO|FIXME|HACK' "Lowlife Ignition/src"
```

## Environment variables

Copy `Lowlife Ignition/.env.example` to an ignored `.env` or `.env.local` for
local development. Add the corresponding variables in the Vercel project's
environment settings for previews and production. Never commit real tokens.

| Variable                        | Exposure           | Purpose                                                                                                                                                                                                      |
| ------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `VITE_SHOPIFY_DOMAIN`           | Browser-visible    | Shopify domain in `store.myshopify.com` form. It is used to construct Storefront API URLs and is also the server-side fallback domain for newsletter calls.                                                  |
| `VITE_SHOPIFY_STOREFRONT_TOKEN` | Browser-visible    | Storefront API access token used by product, content, and cart requests. The `VITE_` prefix deliberately makes it available to client code; grant only Storefront scopes intended for public storefront use. |
| `SHOPIFY_ADMIN_DOMAIN`          | Server-only        | Shopify domain used by the newsletter Admin API endpoint. It may be omitted when the runtime also exposes `VITE_SHOPIFY_DOMAIN`, but setting it explicitly keeps server configuration clear.                 |
| `SHOPIFY_ADMIN_ACCESS_TOKEN`    | Server-only secret | Admin API token used to upsert customers and record email marketing consent. It requires `write_customers` and protected customer-data access. Never prefix it with `VITE_` or expose it to browser code.    |

`isShopifyConfigured()` intentionally considers only the two `VITE_` Storefront
variables. Newsletter writes additionally require the two server-side Admin
settings; if they are absent, the popup retains its current graceful,
toast-only fallback.

## Branching and continuous integration

The short policy is maintained in `README.md`: create
`feature/<short-description>` from `develop`, open a pull request back into
`develop`, and promote `develop` to `main` through a release pull request. Do not
merge feature branches directly to `main`.

The GitHub Actions job named `CI` runs for pushes to `develop`/`main` and pull
requests targeting either branch. Using Node 24 and `npm ci`, it runs:

1. `npm run lint`
2. `npm run typecheck` (`tsc --noEmit`)
3. `npm run build`

Lint catches consistency and React-rule regressions, typecheck validates the
cross-layer contracts, and the production build exercises TanStack/Nitro
bundling and the no-credentials Shopify fallback path. All must pass before
merge. Classic branch-protection rules are intended to make that check
mandatory, but still require manual setup as described below.

## Known gaps and production checklist

- **No provisioned Shopify store:** There is no live domain or token yet. The
  deployed preview renders local mock products and content. Product queries,
  cart mutations, checkout redirects, article queries, metaobject field names,
  token scopes, and Admin customer writes still require validation against the
  real store.
- **Video embeds are placeholders:** `VIDEO_POSTS` uses local thumbnails and
  null `embedUrl` values. Real TikTok/Instagram embed URLs and their browser
  behavior still need to be supplied and tested.
- **Owner Spotlight lacks attribution:** Owner names, build nicknames,
  Instagram handles, and approved captions are placeholders. The
  `TODO(client-content)` and `TODO(owner-data)` comments identify the exact
  component and records that need client-provided information before production.
- **Ticketing is a demo:** Events render from local mock data, and the dialog
  displays a generated QR-style SVG that is not a real ticket. The
  `TODO(shopify)` in `Events.tsx` must be replaced with the actual
  ShopTickets/Ticket Spot purchase and fulfillment flow.
- **Newsletter needs real Admin credentials:** The server route and mutations
  exist, but require a custom Shopify app, `write_customers`, protected
  customer-data approval, and live end-to-end consent testing.
- **Metaobjects must be created in Shopify:** The integration expects public
  metaobject types named `gallery_item` and `spotlight_build`, with field keys
  matching `operations.ts`/`hooks.ts`. Those definitions and Storefront access
  must be configured in the future store.
- **GitHub protection is not yet active:** The authenticated automation token
  lacks repository Administration-write permission. Apply rules for `develop`
  and `main` manually in GitHub's UI (or with an appropriately scoped token) to
  require pull requests, the strict `CI` check, and conversation resolution
  while disallowing force pushes and branch deletion.
- **Vercel ownership is agency-side:** Before a client handoff, decide whether
  the Vercel project and production environment variables remain agency-managed
  or move to a client-owned account.
